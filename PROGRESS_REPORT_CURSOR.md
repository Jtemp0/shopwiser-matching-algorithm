## Что сделано по этапам

### 1. Карта репозитория и доставляемого

- Пайплайн: нормализация → rule-based (`rule_matcher`) → ML (`ml_matcher`) → **ensemble** (ребра из двух источников, Kruskal + ограничения по ритейлерам и размеру кластера).
- Основной CSV результата на конец работы: **`data/outputs/ensemble/ensemble_clusters.csv`** (канон после очистки репо).

### 2. Анализ false positives

- Прогнаны **`scripts/audit_clusters.py`** и **`scripts/review_metrics.py`** на доставляемом CSV (на разных итерациях — v13 и затем «строгий» ensemble).
- Добавлен/уточнён **`scripts/export_fp_candidates.py`**: склейка **strong / weak** флагов (audit-style vs probe из TF-IDF + Jaccard и структурные проверки из методики ревью) и экспорт в один файл для очередей проверки.
- **`scripts/improvements/audit_flavour_failures.py`**: аудит по расширенному словарю на `normalized_name`; артефакт перенесён в **`data/outputs/fp_analys/`**.

### 3. LLM-проверка (Haiku, экономичные батчи)

- **`scripts/llm_fp_spotcheck.py`**: случайная выборка кластеров, батчи по многим кластерам за один запрос, вывод в CSV.
- Уточнён промпт: для **брендовых** SKU — жёсткое «то же SKU», для **собственных марок ритейлеров** — явное правило «эквивалент СТМ при том же core и tier», чтобы модель не завышала FP только из‑за «разный supermarket brand».

### 4. Выводы по качеству и изменениям коду

- Сильный сигнал по данным: **несогласованность размера**, конфликтующие бренды/варианты, низкая текстовая близость внутри кластера — коррелируют с ошибками.
- В **`src/shopwiser/ensemble/main.py`**: при объединении в Kruskal добавлена **жёсткая валидация** набора товаров (конфликты через **`check_hard_conflict`**, порог по **Jaccard** на токенах нормализованных имён, размер/бренд/tier/смешение branded↔own-brand по тем же идеям, что и в аудите).
- В **`src/shopwiser/conflict_tokens.py`**: расширены токены и правила (например уровни «остроты», дополнительные дискриминаторы формата/варианта, нормализации вроде bulgar/bulgur), чтобы отсечь типичные FP без усложнения ML.

Итог по компромиссу: **выше precision / ниже coverage** (меньше 4-way и строк в доставляемом файле) — осознанная точка на кривой precision–coverage, согласованная с критикой Дариуса и контрактным акцентом на сопоставимости товаров.
